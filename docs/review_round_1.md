## 一、项目整体评估

### 1.1 优点

- **定位清晰**：轻量本地文档工具，无网络、无账号、无隐私顾虑，范围控制得当。
- **技术选型稳健**：Kotlin + Jetpack Compose + MVVM + DataStore/Room，均为 Android 官方推荐栈。
- **架构分层合理**：`DocumentParser` 接口实现格式解耦，新增格式只需实现接口，可维护性好。
- **隐私与存储合规**：纯 SAF 方案，不申请 `MANAGE_EXTERNAL_STORAGE`，不联网，用户隐私零风险。

### 1.2 核心短板（电子书阅读器视角）

| 缺失能力 | 严重程度 | 说明 |
|-----------|----------|------|
| epub 仅"纯文本提取" | **严重** | 无图片、无 CSS、无超链接。绝大多数 epub 电子书将无法正常阅读，使其从"阅读器"降级为"epub 文本提取器" |
| 全文搜索/查找 | **严重** | 阅读器与编辑器的最基础需求，无法在文档内定位内容 |
| 文本选择与复制 | **高** | 阅读中有价值的段落无法选中复制，交互体验严重受限 |
| 书签/标注 | **中** | 仅有被动进度恢复，缺少用户主动标记位置的能力 |
| 翻页模式 | **中** | 全文仅有滚动模式，缺少电子书标配的仿真翻页 |
| md 大纲/TOC 跳转 | **中** | epub 有章节跳转，md 却没有对应能力，功能不对等 |

## 二、《需求说明书》评审意见

### 2.1 编号规范问题

`F2.3`、`F2.3a`、`F2.3b` 并列，形成了不规范的三级编号。

**建议**：改为 `F2.3` 字号行距、`F2.4` 字体方案、`F2.5` 阅读主题，后续编号顺延。

### 2.2 功能缺漏

| 缺失功能 | 严重程度 | 说明 |
|-----------|----------|------|
| 全文搜索/查找 | **严重** | 阅读器和编辑器的基础需求，无检索能力体验极差 |
| 文本选择与复制 | **高** | 段落有价值却无法复制 |
| 书签/标注 | **中** | 仅有进度恢复不够，用户需要主动标记 |
| 翻页模式 | **中** | 电子书用户核心习惯 |
| md 大纲/TOC 跳转 | **中** | epub 有章节跳转，md 没有，能力不对等 |
| 跟随系统深色模式 | **偏低** | F2.9 设为低优先级，但这已是 Android 应用的基本预期 |

### 2.3 具体条目问题

- **F2.4 编码探测**：仅提及 UTF-8、GBK，未覆盖 UTF-16LE/BE 和 Latin-1。设计文档中 TxtParser 提到了 UTF-16，需求应与设计对齐。
- **F3.3**："可独立或联动调节"表述模糊——究竟是每文件独立设置还是全局共享？需求本身不明确。
- **非功能需求**：缺少**无障碍（Accessibility）**要求——最低对比度、TalkBack 支持、最小触摸目标（48dp）等均未提及。

### 2.4 总体评价

覆盖了核心的格式支持和排版能力，但遗漏了搜索、选择、书签这些本质需求。作为 V1.0 可以接受"先 MVP"，但建议在文档中明确标注为后续版本规划。

## 三、《软件设计文档》评审意见

### 3.1 严重问题

#### 3.1.1 默认字体前后矛盾（阻塞级）

需求 F2.3a 明确默认字体为"代码风格 (CODE)"，但设计文档 3.1 节 `ReadingSettings` 中默认值为 `ReaderFont.SANS`：

```kotlin
val font: ReaderFont = ReaderFont.SANS,  // ← 应为 ReaderFont.CODE
```

**这是一个需求-设计不一致的 Bug，必须修正。**

#### 3.1.2 epub3 完全未覆盖

设计文档只提及 NCX 导航，但 **epub3 标准使用 `nav.xhtml` 而非 NCX**。epub3 格式电子书目前已占主流，当前设计无法兼容。

**建议**：加入降级策略——优先解析 nav.xhtml，若不存在则回退 NCX。

#### 3.1.3 数据模型设计不够合理

```kotlin
data class Document(val chapters: List<Chapter>)
```

对 txt/md/xml 来说，`chapters` 永远只有一个元素，语义不对。

**建议**使用密封类区分：

```kotlin
sealed class Document {
    data class SingleSection(val paragraphs: List<String>) : Document()
    data class MultiChapter(val chapters: List<Chapter>) : Document()
}
```

### 3.2 重要问题

#### 3.2.1 编码探测算法过于简陋

"按 UTF-8 尝试解码，失败回退 GBK"——一段合法的 GBK 中文文本可能被 UTF-8 解码"成功"但产生乱码，误判率很高。

**建议**：使用成熟编码探测库（如 Mozilla UniversalCharsetDetector / juniversalchardet），或至少加入字节频率统计分析。

#### 3.2.2 阅读主题用 `Long` 存颜色

```kotlin
enum class ReadingTheme(val background: Long, val foreground: Long)
```

`Long` 存颜色极易出错（有无符号、ARGB 顺序混乱）。

**建议**：使用 Compose 的 `Color` 类型，或标准化的 `@ColorInt` / `@ColorLong` 注解。

#### 3.2.3 自定义字体验证不足

"加载失败自动回退 CODE + 提示"——缺少**导入时**的预验证。应在导入后立即尝试构建 `FontFamily` 并检查 `Typeface`，而非等到渲染时才暴露出错误。

#### 3.2.4 编辑器 SAF 写回的风险

`ContentResolver.openOutputStream(uri, "wt")` ——并非所有 SAF Provider 都支持 `"wt"` 截断模式。

**建议**：捕获 `FileNotFoundException` 或 `UnsupportedOperationException`，回退到先删除再写入。

#### 3.2.5 解析层缺少协程取消支持

epub 解析在 `Dispatchers.IO` 执行，用户快速返回/切换文件时，未完成的解析任务应通过协程取消来中止，避免资源浪费和内存泄漏。

**建议**：加入 `job.cancel()` 或 `ensureActive()` 检查。

#### 3.2.6 `runCatching` 包裹粒度过大

所有解析统一用 `runCatching` 兜底，用户永远只看到"文件损坏"，无法区分具体原因（缺 OPF vs XHTML 格式错误 vs 内存不足）。

**建议**：分类捕获异常并给出差异化提示。

### 3.3 细节问题

| 问题 | 位置 | 说明 |
|------|------|------|
| Room 对简单场景过重 | 3.5 节 | 最近文件仅 50 条简单记录，用 DataStore 存 JSON 更轻量且减少 APK 体积 |
| LazyColumn 未说明预取策略 | 6 节 | 仅说"首屏 200 段"，未说明滚动时的预取窗口大小，快速滑动可能白屏 |
| 缺少内存压力处理 | 全局 | 大文件 + ViewModel 持有全量 Document 可能 OOM，应有 `onTrimMemory` 或 LRU 策略 |
| `ReadingTheme` 枚举值的颜色名称 | 3.1 节 | `DEFAULT` 背景色 `0xFFFFFFFF` 与前景色 `0xFF1B1B1F` 对比度过高，长时间阅读不舒适（纯白 + 深灰黑） |

## 四、《测试用例》评审意见

### 4.1 用例覆盖缺失

| 缺失场景 | 建议优先级 | 原因 |
|----------|------------|------|
| UTF-16LE/BE 编码文件 | **P0** | 需求与设计都提到支持 UTF-16，但无测试用例 |
| epub3（nav.xhtml 导航） | **P0** | 设计补充 epub3 支持后必须追加验证 |
| epub XHTML 内部编码非 UTF-8 | **P1** | 有些 epub 内嵌的 XHTML 可能为 GBK 等编码 |
| 超多章节 epub（>100 章） | **P1** | 章节列表性能、滚动流畅度 |
| epub 嵌套 ToC（>3 级） | **P2** | NCX navMap 可达多层，边界测试 |
| RTL 文本（阿拉伯语/希伯来语） | **P2** | 虽定位中文用户，排版异常仍需被兜底 |
| 文件名含特殊字符（`#%&` 等） | **P1** | URI 编码处理不当会导致 SAF 打开失败 |
| 编辑时进程被杀后恢复 | **P1** | TC-F4-05 排除了"进程被杀"，但应有 `onSaveInstanceState` 覆盖 |
| 并发打开同一文件 | **P2** | 两个入口同时打开同一 URI 的行为未定义 |
| 冷启动后连续打开/关闭 10 个文件 | **P1** | 内存泄漏检测 |

### 4.2 现有用例问题

#### 4.2.1 TC-F2-01
"含超长行"未量化。**建议**：明确超长行定义（≥ 500 字符或 ≥ 2 倍屏幕宽度）。

#### 4.2.2 TC-F2-06
"默认值适中"是主观判断，且应为 P0——默认值错误直接影响所有用户首次体验。

#### 4.2.3 TC-F2-14
仅测 UTF-8/GBK，缺 UTF-16、Latin-1 编码文件。

#### 4.2.4 TC-UT-12
"换行模式切换定位"被归类为"单元测试"，但实际依赖 UI 层段落索引机制，应为集成测试或 Compose UI 测试。

#### 4.2.5 测试夹具 `DengXian.ttf`
微软等线是商业字体，不可在项目中分发。**建议**：文档中应描述为"用户自备的任意合法 ttf 字体文件"。

#### 4.2.6 TC-F4-02 性能指标
需求中 1MB ≤ 1s，测试中 8MB ≤ 3s——建议统一标准，或分级给出期望值。

## 五、总结与建议

| 优先级 | 行动项 |
|--------|--------|
| **阻塞** | 修正设计文档中默认字体 `SANS → CODE` 的不一致 |
| **阻塞** | 需求中加入全文搜索功能（若 V1.0 不做，至少在文档中标注为 V1.1 规划） |
| **高** | epub 解析加入 epub3 nav.xhtml 支持 |
| **高** | 编码探测改用成熟库方案，补充对应测试用例 |
| **高** | `ReadingTheme` 颜色类型从 `Long` 改为 Compose `Color` |
| **高** | `runCatching` 细化错误分类，给出差异化提示 |
| **中** | 考虑加入文本选择/复制功能 |
| **中** | 补充无障碍（Accessibility）需求 |
| **中** | 补全缺失的边界测试用例 |
| **中** | 评估 Room vs DataStore 对"最近文件"场景的取舍 |
| **低** | 加入内存压力处理（`onTrimMemory`） |
| **低** | 加入协程取消支持 |

### 总体结论

项目作为 V1.0 MVP 定位清晰、技术方案克制。三份文档结构完整，需求→设计→测试的可追溯性良好。主要短板集中在 **(1) epub 支持深度不足**（难以作为合格电子书阅读器），以及 **(2) 基础交互能力缺失**（搜索、选择）。若这两块能得到补强，会成为一个有竞争力的轻量级阅读工具。
