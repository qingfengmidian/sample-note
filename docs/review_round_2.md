## 一、阻塞项（必须修正后方可进入开发）

### 1.1 版本号命名冲突：V1.1 既是当前版本又是规划版本

**需求说明书** 第 5 章"后续版本规划"中：

| 功能 | 计划版本 |
|------|----------|
| 全文搜索/查找 | **V1.1** |

但文档头部的版本号已经是 **V1.1**。

这造成了一个逻辑矛盾：当前文档就是 V1.1，但 V1.1 也作为未来的规划版本出现。`V1.2`、`V1.3` 同理被挤占了命名空间。

**建议**：将 V1.1 改为 V1.0（表示当前发布版本），后续规划改为 V1.1 / V1.2 / V1.3。当前三份文档版本号回退为 V1.0（或改成 V1.0-REV1 之类的修订标识），让版本号体系自洽。

### 1.2 `SavedStateHandle` 对超大编辑文本存在序列化风险

设计文档 3.4 节：

> 编辑文本、光标位置与 `dirty` 经 `SavedStateHandle` 持久化，进程被杀重建后恢复到编辑现场。

`SavedStateHandle` 底层经 `Bundle` 序列化，Android 的 `Bundle` 跨进程传输限制约为 **1 MB**（实际因厂商而异，通常 ≤ 500 KB 就触发 `TransactionTooLargeException`）。设计文档 3.4 节允许编辑上限 10 MB 的文件——将全量文本塞入 `SavedStateHandle` 几乎必然崩溃。

**建议**（三选一）：
- **方案 A**：限制 `SavedStateHandle` 仅存储在编辑文件中 ≤ 100 KB 以内的文本，超出部分走临时文件缓存（应用私有目录下的 `edit_recovery/`）。
- **方案 B**：`SavedStateHandle` 仅存 `dirty` + 光标位置 + `uri`，不存全文本。进程重建后从原文件重新加载，对比原始内容推断用户改动（diff 还原）。
- **方案 C**：明确限制 `SavedStateHandle` 恢复仅对 ≤ 500 KB 的文件生效，超出则降级为仅恢复 `dirty` 标记 + 光标位置。

无论选哪种，需要在**设计文档** 3.4 节和**测试用例** TC-F4-06/TC-UI-05 中明确说明覆盖范围。

## 二、重要问题（强烈建议修正）

### 2.1 juniversalchardet 的维护状态与 R8 风险

设计文档选定 juniversalchardet 作为编码探测库，该库存在两个风险：

1. **长期未维护**：Maven Central 上最新版本 1.0.0 发布于 2018 年，此后未再更新。在 AGP 8.x + R8 full mode 下的兼容性未经验证。
2. **R8 Keep 规则空泛**：设计文档仅说"需加 `-keep` 规则（其内部按类名反射加载探测器）"，未给出具体规则。实际需保留约 5~6 个探测器类（`UniversalDetector`、各 `CharsetProber` 子类等），缺规则会导致 R8 把探测器类移除，所有文件都回落 GBK/Latin-1。

**建议**：
- 在集成前对 juniversalchardet 做一次 smoketest，验证 R8 后 UTF-8/GBK/UTF-16 探测仍正常。
- 在设计文档 6 节中补齐具体的 ProGuard 规则，至少给出关键类名。
- 或者评估替代方案：`ICU4J` 的 `CharsetDetector`（Google 维护、Android 部分内置），虽体积更大但可靠性更高。作为中优先级备选方案在设计文档备注。

### 2.2 缺少 epub 解析的性能测试

当前性能测试 TC-F4-02 仅覆盖 txt 文件（1 MB / 8 MB），但没有 epub 解析的性能场景。epub 的解析瓶颈与 txt 完全不同：

- 100+ 章的 epub（`many_chapters.epub`）需要逐一打开 ZIP 内多个 XHTML 条目，每个条目都做一次 XML 解析，I/O 模式是多次小读取而非一次大读取。
- 嵌套 TOC（`nested_toc.epub`）需要递归构建章节树。

**建议**：
- 新增性能用例：打开 `many_chapters.epub`（> 100 章），要求首章显示 ≤ 3 s，章节列表打开 ≤ 1 s。
- 或至少在单元测试中加入 EpubParser 的解析耗时断言（给定最小 epub fixture，解析 ≤ 200 ms）。

### 2.3 `ParseException.MalformedContent` 的 null 安全问题

设计文档 3.1 节：

```kotlin
class MalformedContent(cause: Throwable) :
    ParseException("内容解析失败：${cause.message}")
```

当 `cause.message` 为 `null`（如 `NullPointerException` 无 message）时，提示将变为 **"内容解析失败：null"**。

**建议**：
```kotlin
class MalformedContent(cause: Throwable) :
    ParseException("内容解析失败：${cause.message ?: cause::class.simpleName}")
```

### 2.4 三文档对 epub 内嵌 XHTML 编码的表述不完全对齐

| 文档 | 表述 |
|------|------|
| 需求说明书 | 仅说"兼容 epub2/epub3 导航"，未提及章节内编码 |
| 软件设计 | "XmlPullParser 自动按 XML 声明处理章节内编码（含非 UTF-8 内嵌 XHTML）" |
| 测试用例 | TC-F2-17a 测试内嵌 GBK XHTML，但有断言"XmlPullParser 按 XML 声明编码解析" |

实际 epub 规范要求 XHTML 必须为 UTF-8 或 UTF-16，非 UTF-8 的内嵌 XHTML 属于**非标准 epub**。设计文档描述为"正常能力"，测试用例描述为正例，容易误导：XmlPullParser 确实能处理 XML 声明的编码，但如果 XHTML 声明了 GBK 但实际 XML 声明写的是 UTF-8（常见于不规范 epub），XmlPullParser 按声明处理反而出乱码。

**建议**：
- 设计文档 3.2 节将"章节内编码"表述改为防御性处理：优先信任 XML 声明，解析失败时回退 UTF-8 重试。
- 测试用例 TC-F2-17a 增加一个负例：XHTML 声明 UTF-8 但实际内容为 GBK 字节流，验证不崩溃且给出可读降级结果。

## 三、中等问题

### 3.1 需求说明书：后续版本规划中的 epub 富文本路由不清晰

需求说明书 5 章：

> epub 富文本渲染 | 视需求再评估 | 图片/CSS/页内链接，脱离"纯文本提取"定位后另行立项评估

这等于说 V1.0 的 epub 能力是一个**可能永远不会被升级**的临时方案。"视需求再评估"意味着如果团队决定不做，epub 将永远停留在纯文本提取水平。

**建议**：至少给出一个评估时间节点（如"V1.3 发布后评估用户反馈决定是否立项"），让路线图有可预期性。

### 3.2 设计文档：`ContentResolver.openOutputStream(uri, "w")` 回退方案的原子性问题

3.4 节 SAF 写回策略为 `"wt"` 失败 → 回退 `"w"` → 仍失败提示另存。

`"w"` 模式按文档是 truncate + write，但**部分云存储 Provider**（Google Drive、OneDrive）的 `openOutputStream` 实现会先清空文件再写入。如果写入过程中发生异常（网络中断、配额超限），原文件已经被清空但新内容未写入完成，导致**数据丢失**。

**建议**：
- 在保存流程中先写临时文件（应用缓存目录），校验完整性后经 SAF 一次性写回。
- 或至少在设计文档 8 节风险表中新增一行："SAF 写回中途失败导致原文件截断"→"先写临时副本再覆盖"。

### 3.3 测试用例：TC-F4-06 未说明编辑文本大小

> TC-F4-06 | 编辑中进程被杀恢复 | 编辑有未保存修改 | 切后台后通过开发者选项/adb 杀死进程，重新进入该文件编辑页 | 经 SavedStateHandle 恢复编辑现场

此用例未指定编辑内容的体积。基于 1.2 的分析，建议明确为"编辑一段 ≤ 100 KB 的文本"（若采用限制方案），或按所选恢复方案补充大文本的降级测试。

### 3.4 测试用例：缺少 Latin-1 编码的功能级测试

TC-F2-14（编码自动识别）覆盖了 UTF-8/GBK/UTF-16LE/BE/BOM，但需求 F2.6 提到的 Latin-1 兜底仅在单元测试 TC-UT-03b 中覆盖（纯极端字节流）。

**建议**：新增一条 P1 功能测试：打开一个真实的 Latin-1（ISO 8859-1）编码 txt 文件（含西欧特殊字符如 é、ü），验证自动识别并显示正确。

### 3.5 测试用例：TC-F4-08 覆盖不够细致

> TC-F4-08 | 解析取消 | 打开 `many_chapters.epub` | 解析进行中立即按返回 | 解析协程被取消，界面正常退出，无后台残留任务

仅说"无后台残留任务"，但未说明如何验证。建议：明确验证手段——退出后稍等 2 秒再进入同一文件，确认从零开始重新解析（非复用残留半成品），且文件句柄无泄漏（可通过 `lsof` 辅助验证）。

### 3.6 设计文档：`EpubParser` 降级链中 XHTML 剥标签正则的风险

设计 8 节：

> XHTML 解析失败时退化为"剥标签"正则提取

正则剥标签在处理 CDATA 块、注释中的 `</script>` 误匹配、内联的 `&lt;` 实体等边界情况时容易出错。

**建议**：标注该降级路径仅为最后保底策略（已有 XmlPullParser 正式路径），正则提取结果只要"可读"即可，不追求精确还原。

### 3.7 需求说明书：系统主题联动优先级偏低

F2.11 仍然是"低"优先级，对应测试 TC-F2-12/13 也是 P2。但作为一个 2026 年面向 Android 8.0+ 的应用，跟随系统深色/浅色模式已是用户的基本预期。

**建议**：至少提升为"中"优先级，测试相应提为 P1。

### 3.8 设计文档：DEFAULT 主题纯白背景（重申）

上轮评审中已提及，但未采纳。这里重申——`Color(0xFFFFFFFF)` 纯白背景在 OLED 屏幕上长时间阅读刺眼。大量主流阅读 App 的默认浅色主题使用的是微淡灰白（如 `#F5F5F5` 或 `#FAFAFA`），既保持了"白色"的视觉感知，又降低了屏幕亮度冲击。

建议将 DEFAULT 背景色改为 `Color(0xFFFAFAFA)`，不影响功能，仅改善阅读舒适度。

### Round 2 总体评价

V1.1 修订较好地消化了 Round 1 的大多数意见，编码探测、epub3、异常分类、协程取消等关键问题的处理质量有显著提升。**两个阻塞项（版本命名冲突、SavedStateHandle 超限风险）应在进入开发前修正**，其余问题可在开发过程中逐步解决。三文档之间的一致性维护良好，需求→设计→测试的可追溯链完整。
